## 2. 실행 환경 분석

- PC: 삼성 갤럭시북4 (NT750XGP-G72AG)
  - CPU: Intel Core 7 150U (10코어) / RAM: 32GB / GPU: MX570A (VRAM 2GB)
- 판단:
  1. VRAM 2GB → GPU 추론 불가, **CPU 추론(llama.cpp/Ollama)** 채택
  2. RAM 32GB → 7.8B Q4 모델(약 5GB)도 메모리 여유 충분
  3. 예상 속도: 2.4B 약 15~25 token/s (실사용 쾌적) / 7.8B Q4 약 4~8 token/s (다소 느림)

### 2.1 LLM 이중 구성

| 구분 | 모델 | 용량 | 용도 |
|---|---|---|---|
| 기본 | **EXAONE 3.5 2.4B** (Q4) | ~1.6GB | 일상 질의, 빠른 응답 |
| 고품질(선택) | **EXAONE 3.5 7.8B** (Q4) | ~4.8GB | 복잡한 법령 해석, UI 토글로 전환 |

- 임베딩: **BGE-M3** (한국어 포함 다국어 최상위, 로컬 구동, ~2.3GB) — 대안: KURE-v1
- 모든 모델은 구축 단계에서 1회 다운로드 후 영구 오프라인 사용

## 3. 시스템 아키텍처

```
┌─ A. 구축 파이프라인 (인터넷 필요, 1회/자료 갱신 시) ─────────┐
│ PDF 24건                                                      │
│  → ① 텍스트 추출 (PyMuPDF, 페이지 번호 보존)                 │
│  → ② 청크 분할: 법령은 "조문 단위", 보고서는 500자+오버랩    │
│  → ③ BGE-M3 임베딩 → ChromaDB 저장 (메타: 문서명·조문·쪽)   │
│  → ④ UMAP 3D 좌표 사전 계산 → embeddings_3d.parquet         │
└──────────────────────────────────────────────────────────────┘
┌─ B. 질의응답 (완전 오프라인) ────────────────────────────────┐
│ 질문 → 임베딩 → ChromaDB 유사도 검색 (top-k=5)               │
│  → EXAONE이 검색 청크 기반 답변 생성 (Ollama, 스트리밍)      │
│  → 답변 + 근거 카드(조문·쪽) + 원문 expander                 │
│  → 3D 임베딩 지도에 검색 청크 하이라이트                     │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 청크 분할 전략 (법령 특화 — 핵심 품질 요소)

1. 법령·조례: 정규식으로 `제N조(제목)` 단위 분할 → 조문 번호가 그대로 출처가 됨
2. 기본계획·지침 등 보고서형: 목차 절 단위 우선, 길면 500자 + 100자 오버랩
3. 각 청크 메타데이터: `{문서명, 법령구분, 조문번호, 페이지, 시행일자}`

### 3.2 "입체적 단어구조" 3D 시각화

1. 전체 청크(예상 1,500~2,500개)를 UMAP으로 3차원 축소 → Plotly `Scatter3d`
2. 문서별 색상 구분 → 법령 간 의미적 군집 구조가 입체로 보임
3. 질문 시: 질문 위치(★) + 검색된 top-k 청크 강조 표시 → "챗봇이 어디서 답을 찾았는지" 직관적 확인
4. 기존 대시보드와 동일한 Plotly 스택 → Tab51 통합 시 추가 의존성 없음

## 4. 기술 스택

| 구성요소 | 선정 | 사유 |
|---|---|---|
| LLM 런타임 | Ollama (Windows) | 설치 간편, 오프라인, 모델 전환 용이 |
| LLM | EXAONE 3.5 2.4B / 7.8B | 한국어 성능 동급 최강, 경량 |
| 임베딩 | BGE-M3 (sentence-transformers) | 한국어 검색 정확도 상위, 로컬 |
| 벡터DB | ChromaDB (persistent) | 파일 기반, 서버 불요, 백업 = 폴더 복사 |
| PDF 추출 | PyMuPDF (fitz) | 한글 PDF 추출 안정성 |
| 차원축소 | umap-learn | 3D 시각화 |
| UI | Streamlit (`st.chat_message` + fragment) | 기존 대시보드와 동일 |

- 신규 패키지: `ollama, chromadb, sentence-transformers, pymupdf, umap-learn` (requirements에 `# Tab51 챗봇` 섹션 분리)
- 예상 디스크 사용: 모델 ~4GB(2.4B 기준) + 벡터DB ~200MB + 임베딩모델 ~2.3GB ≈ **총 7GB 내외**

## 5. 모듈 구조 (별도 개발 → 통합 전략)

```
src/chatbot/                      # ★ 독립 모듈 (대시보드 무의존)
├── __init__.py
├── config.py                     # 모델명·경로·top_k 등 설정
├── ingest/
│   ├── pdf_loader.py             # PDF → 텍스트+페이지
│   ├── chunker.py                # 조문 단위 분할
│   └── build_index.py            # 임베딩→ChromaDB→UMAP (CLI 실행)
├── rag/
│   ├── retriever.py              # 검색
│   ├── generator.py              # Ollama 호출, 스트리밍, 프롬프트
│   └── pipeline.py               # 질문→답변+출처 통합
├── viz/
│   └── embedding_3d.py           # Plotly 3D 지도
└── standalone_app.py             # 단독 테스트용 Streamlit 앱

data/07_chatbot/
├── *.pdf                         # 원본 (현행 유지)
└── index/                        # 생성 산출물
    ├── chroma/                   # 벡터DB
    └── embeddings_3d.parquet     # 3D 좌표

src/dashboard/tabs/tab51_chatbot.py   # Phase 4: 얇은 래퍼만 추가
```

- **통합 방식**: `tab51_chatbot.py`는 `src/chatbot/`을 import해서 렌더링만 담당 → 기존 tab01~43 패턴과 동일. 챗봇 오류가 대시보드 전체에 영향 주지 않도록 try/except 격리 + Ollama 미설치 시 안내 화면 표시.

## 6. 단계별 개발 일정

| Phase | 내용 | 산출물 | 예상 |
|---|---|---|---|
| **0. 환경 구축** | Ollama 설치, EXAONE·BGE-M3 다운로드 (인터넷) | 모델 구동 확인 | 0.5일 |
| **1. 인덱싱 파이프라인** | PDF 추출→조문 청크→ChromaDB→UMAP | `build_index.py`, index/ 폴더 | 1~2일 |
| **2. RAG 코어** | 검색+생성+출처 추적, 프롬프트 튜닝 | `pipeline.py` + CLI 테스트 | 1~2일 |
| **3. 단독 챗봇 UI** | 채팅 UI + 근거 카드 + 3D 지도 | `standalone_app.py` | 1~2일 |
| **4. Tab51 통합** | 대시보드 통합, 오프라인 검증, 문서화 | `tab51_chatbot.py`, CHANGELOG | 1일 |
| **5. 품질 검증** | 법령 Q&A 30문항 골든셋 평가, 환각 점검 | 평가표, 수정 반영 | 1일 |

- 합계 약 **5.5~8.5일** (Cowork 세션 기준 수 회 분할 수행 가능)

### 6.1 Phase 5 검증 방법

1. 골든셋: 실무 빈출 질문 30개 (예: "지하수 개발·이용 허가 유효기간은?", "제주도 조례상 원수대금 부과 기준은?") — 박사님께서 10개 내외 실무 질문 제공해 주시면 품질이 크게 향상됩니다
2. 평가: 정답 포함 여부, 출처 정확성(조문·쪽), 환각 여부 3개 축
3. 오답 유형별 대응: 검색 실패→청크 전략 수정, 생성 오류→프롬프트 수정
